## Project description

Honeyweb turns an authorized application source snapshot into a connected synthetic deception environment that can be regenerated as the application changes. A local scanner extracts mounted Express routes, TypeScript interface fields or Prisma scalar models, and supported references. Meta designs a branching graph of credential-gated collections and exports; a constrained runtime supplies related synthetic records with consistent foreign keys and stateful exports.

A second Meta-driven explorer knows only an entry URL. It discovers links from HTTP responses, chooses bounded read-only requests, and checks observed record relationships and export consistency. The dashboard shows its actions, correlated demo telemetry, schema drift, affected endpoints, and checks before and after regeneration. A custom authorized source root can use the same workflow.

The prototype includes a reproducible fixture evaluation and an adapted case study on a pinned existing RealWorld Express/Prisma backend. The case study starts the actual application with disposable PostgreSQL, compares Meta-generated and deterministic connected graphs in repeated raw-HTTP discovery trials, and checks regeneration after an actual schema change. It measures discovery coverage, consistency, latency and tokens. It is a local research prototype; the simulation does not establish real-attacker deception or detection effectiveness.

A subsequent frozen objective-driven pilot ran 18 matched internal-data tasks and three benign public-read controls. Neither graph caused a confirmed decoy submission. Meta produced early decoy contact in 1/6 tasks versus 2/6 for the deterministic graph; no-decoy capability controls passed 4/6. All benign controls completed without decoy contact. The initial response-format failure, narrow transport correction and scoring evidence for every final session are retained; response record contents are omitted from publication. These results identify entry, credential and fixture credibility gaps; they do not demonstrate a Meta advantage.

A later blind intrusion pilot supplied ordinary member accounts and restricted-data goals without telling agents a deception system existed. Agents chose GET/POST requests against two deliberately introduced flaws in an isolated lab extension. Meta-generated Honeyweb produced one server-verified early catch in six attacks, compared with zero for ordinary monitoring and deterministic decoys. That agent reused an issued credential, read a protected decoy collection and downloaded its export; five other Meta-condition attacks reached the actual target. All nine benign tasks completed without alerts. Both secure-control sessions ended with execution errors, so the overall efficacy evaluation is inconclusive. All 29 outcomes and the frozen protocol are public; these flaws are not attributed to upstream RealWorld.

Version 0.3 addresses the first pilot's visible giveaways with neutral served labels, opaque service credentials and coherent fictional records. It adds a manually authored editorial adapter inside normal application route families, with private review copies, revision history, profile mutations and consistent export jobs. A separate containment condition redirects later requests into fictional state after a server-confirmed canary hit. This distinguishes attracting an agent from enforcing isolation after detection. The adapter is lab-specific TypeScript, not newly generated Meta behavior or a production identity gateway. The follow-up freezes five conditions before live decisions and preserves every outcome.

The first frozen follow-up completed 37 live sessions without execution errors. Original Honeyweb caught 0/4 attacks early and allowed 4/4 actual protected reads. Presentation changes caught 4/4 but allowed 3/4 reads. Stateful application workflows and the containment condition each caught 4/4 with zero protected reads; containment served eight later requests from fictional state. All 15 benign tasks completed without alerts. Both secure controls met the frozen rule, but the account control stopped at the evaluator's credential guard before exercising the secured endpoint. These are small descriptive lab results, with that limitation retained in the public report. They do not establish a production catch rate, a general Meta advantage, or an incremental prevention benefit of containment over the passive workflow condition.

The v0.4 frontier campaign retired weak treatment arms from active testing and expanded to 208 attempted sessions. Development A caught 16/16 attacks with six benign passes and two exercised secure controls, then the unchanged candidate was frozen. The one-time final run scheduled 100 attacks, 60 benign tasks and 24 controls, varying five route layouts and five goal styles. Model access failures interrupted 116 of 184 final sessions (115 HTTP 403s and one timeout). The conservative result is 40/100 valid early catches; capability and secure control requirements failed, and only 25/60 benign objectives were achieved. Although all 40 error-free attacks were caught, that conditional subset cannot establish a 90% rate. Every failed outcome remains public. Post-run v0.4.1 adds a locally tested access-denial stop guard; it has not undergone another live campaign. The larger efficacy evaluation remains inconclusive pending restored provider access and a fresh frozen protocol.

Version 0.5 generalizes the workflow implementation into a validated source-bound planner and isolated runtime with owned/private records, mutable fields, revisions and export snapshots. A deterministic compiler is the default; an optional structured Meta planner is implemented and contract-tested with mocks, but has not been live-evaluated. Server-issued session identity keeps containment stable across credential rotation while isolating unrelated users. The new campaign engine adds safe provider diagnostics, readiness checks, atomic checkpoints and explicit resume of unstarted assignments. All 69 tests and the build pass, plus 90 scripted HTTP contract cases across three source snapshots. The first live development launch stopped on one HTTP 403 readiness request before any of its 30 agent sessions started; the checkpoint and diagnostic request ID are preserved in [the test record](FRAMEWORK.md#live-test-attempt-november-2-2026). These implementation results do not establish a 90% autonomous-agent catch rate.

## How we use Meta

Meta's `muse-spark-1.3` model is called through the Model API chat-completions endpoint with structured JSON output. One role converts extracted source metadata into graph topology, endpoint names and a rationale. A separate role selects HTTP requests from observations. The dashboard explorer receives discovered links with redacted credentials; the case-study evaluator starts at a homepage, interprets raw HTML/JSON/text without supplied candidates, and may use only credentials it has observed. Those credentials authorize only the synthetic decoy runtime and are redacted from saved evidence. Output validation, synthetic data, credential handling, request constraints and deployment checks are deterministic local code.

## Why Meta models matter

The two model roles adapt to different evidence: source structure for environment design, and incomplete HTTP observations for exploration. This lets us test a generated environment with an observer that was not given its blueprint. The offline policy is explicitly labeled and provides a reproducible development baseline. The live workflow records whether actual Meta-generated plans and action choices complete the evaluation.
